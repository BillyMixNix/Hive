# Current state machine — recorded before production edits

Source: `HIVE-TRANSITION-005-RUNTIME-REPLACEMENT-1/repaired-workshop`, the immutable final TRANSITION-005 source. This reconstruction precedes creating/editing the new implementation copy. Prior reviewer analysis supplies the historical audit; source inspection here additionally found the API's post-review external-baseline integrity override.

1. `workshop/hive.py:_run_build_impl` (1945): copy source to private stage; establish source identity; normalize/validate planner ownership and host scope; dispatch active workers. Worker responses undergo protocol and structural preflight, private staging, targeted verification and bounded correction. Failed targeted edits are restored. Worker failures accumulate in `run.errors`.
2. At 2637, compute changed files, base/staged manifests and diff. External runs with earlier errors or no changed files skip the full gate and store a failed prerequisite result. Otherwise `verify_tree` runs the unchanged isolated verifier; verifier exceptions add a verifier error and a failed result. Store the result in `run.verification`.
3. At 2675, enter `reviewing` and invoke the model even if verification failed. `_reviewer_prompt` (1852) supplies request, `diff[:70000]` and `json.dumps(verification)[:20000]`; the latter may be invalid clipped JSON. Reviewer is read-only and asked to approve only request-matching, narrowly scoped, passing work.
4. A reviewer provider exception (2680) adds a reviewer failure to the same `run.errors` used for worker failures and fabricates `approve:false`, summary `Reviewer call failed.` No semantic decision existed.
5. Otherwise `_parse_agent_json` (836) parses JSON; on syntax failure, makes one same-role repair. `_json_repair_prompt` (814) supplies schema/parser error/previous response but omits original review evidence. Parseable objects are not host-validated against `REVIEW_SCHEMA` (`hive_protocol.py:126`). Parseable scalars can crash later. Exhausted parsing/repair fabricates false approval and adds a run error (2690).
6. Host mutates the model review (2699): force false if verification failed, any run error exists, or no changed files exist. Append generic issues. This mixes host facts and model opinion, and provider errors thereby veto readiness.
7. Store raw output and mutated parsed review in `agents.reviewer`, also store `run.review`. At 2714, truthy `review.get('approve')` produces `status='ready'`; otherwise `rejected`. Confidence/issues do not gate separately. The string `"false"` is truthy. An unusable JSON shape may instead produce outer `failed`.
8. `app.py:hive_build` (795), after the controller returns, checks external baseline/candidate integrity (987). If either changed, adds an external-root error, marks failed, and also rewrites review approval false. This is another conflation of host integrity and model opinion. API completion ledger uses boolean verifier/reviewer fields; completion message and UI depend on `ready`.
9. `static/index.html:renderHiveRun` (490) shows plan/review/errors/diff/checks; apply is enabled only for `ready && verification.passed && review.approve` (526). `workshop/chat_context.py:_run_summary`/`_latest_run_digest` similarly expose reviewer approval as a boolean.
10. `app.py:HiveApplyReq` (220) has `approved: bool=False`. `/api/hive/apply` (1046) checks code mode and explicit approval before calling `hive.apply_run`. No automatic call to apply is made by build completion.
11. `hive._apply_run_locked` (2824) first forbids external-root/candidate-only runs regardless of review. Then requires status ready, passing verification, truthy reviewer approval, and not already applied. Requires base/staged manifests; compares every source and staged file before any backup/write and again immediately before each write. Stale/tampered paths raise `StaleBaseError`.
12. Apply snapshots original files, atomically replaces changed files, runs post-apply verification, records applied only on success. Failure restores original files/removes newly created files. `apply_run` holds a process lock. Human approval is currently enforced at the endpoint, not as an explicit parameter to this core function.

No subsequent worker correction follows reviewer veto. Only review-JSON formatting repair is available. Early planner termination never reaches review; that is not a reviewer rejection.
