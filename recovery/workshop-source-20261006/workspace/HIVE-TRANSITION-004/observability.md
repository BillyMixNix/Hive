# Observability changes and evidence boundaries

The first production revision is diagnostic instrumentation only. It does not change timeout values, Java/Gradle argv, JUnit selectors/assertions/counts, offline/network restrictions, resource limits, copy/hash validation, planner/worker behavior or promotion rules.

- `workshop/verifier_trace.py` creates a unique durable directory outside the candidate. It writes `verification-events.jsonl`, the exact launch argv/cwd/timeout, stdout.log and stderr.log. Docker output is written directly to files rather than discarded pipe buffers on timeout. Test-injected `TimeoutExpired` stdout/stderr is also retained. No partial report can bypass the timeout failure branch.
- Each host event has monotonic and wall timestamps, run ID, elapsed milliseconds and a phase. Container events retain their own monotonic/wall clocks and PID under `source_event`; host receipt time orders the combined JSONL. The two monotonic clock domains are never subtracted. Phase durations within the container use its own elapsed values. Cross-boundary startup intervals use host receipt timestamps and include a small reader delay.
- `verification/jvm_runner.py` emits flushed stderr events for source materialization, frozen-test validation, wrapper/native-input copies, Java discovery, source hashing, Gradle invocation/return, process launch/exit, and JUnit report collection. Pipe readers use `read1` where available to expose small output chunks promptly. The underlying command runner still drains both pipes and retains its existing bounded result tails. Output telemetry is capped at 2,000,000 bytes with an explicit diagnostic-limit event; it does not truncate or change the gate's own result handling.
- Gradle stdout/stderr is streamed in `process_output` events. `> Configure`, `> Task`, and daemon lines are preserved as **output markers**, not invented precise task start/end boundaries. `analyze_timings.py` materializes these streams as child-stdout.log/child-stderr.log for inspection. No source-level Gradle listener or task mutation is injected.
- `workshop/hive_verifier.py` records setup/cache validation and timeout/termination/cleanup. Read-only `docker inspect`, `top` and `stats` samples occur before the deadline. Timeout removal still targets the exact generated container, and post-removal inspection now records whether absence is confirmed. Sanitized-source cleanup records whether its path is gone.
- A read-only bind mount supplies the host-reviewed instrumented JVM runner at its fixed `/opt/verifier/jvm_runner.py` location. Its hash is recorded in every trace. The original image ID, JDK, Python, entrypoint, caches and gate policy stay fixed. Candidate files cannot choose or supply this overlay. This is an explicit apparatus change, not a claim of an unchanged executable image filesystem.
- `hive.targeted_verify` preserves the diagnostic locator and last observed verifier phase in the targeted result, so orchestration does not discard the durable evidence. Validation, snapshot/rollback, correction counts and repeated-proposal rejection are unchanged.

Read-only `/proc` sampling is separately labeled with its duration. It inspects command lines, process state/I/O counters, open descriptors, locks, cgroup counters and network socket tables; it sends no signal, enables no profiler and changes no JVM settings. Its own diagnostic process is excluded from the listing. Process absence and successful Docker removal establish observed container cleanup; missing historical process evidence is not backfilled.

Host secrets/environment are not inventoried. Only fixed explicitly forwarded container/Java environment and task-related commands/paths are logged. Output is untrusted diagnostic data; a printed PASS string, task marker, partial JSON or timeout output never authorizes acceptance.
