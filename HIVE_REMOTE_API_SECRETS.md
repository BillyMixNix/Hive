# API secret handling

Use the remote platform's protected environment secret named `OPENAI_API_KEY`. The implementation only consumes that environment variable; it never accepts a key CLI argument or config/evidence file. Do not paste a credential into chat, a prompt, a model-ID field, source code, a workflow input or a task request. Key creation/account selection belongs in the secure OpenAI Platform setup flow, not this repository.

In GitHub Actions, `hive-api-infrastructure` receives the API secret only in the `smoke` step. Preflight and preparation receive no API key. Checkout uses a read-only repository token and `persist-credentials: false`. Actions artifact-upload credentials belong to the platform step, not to a future candidate runtime. Review the exact dispatch commit before injecting a secret: code from that commit is trusted orchestration, not a sandbox for malicious repository maintainers.

`OpenAIProvider` removes `OPENAI_API_KEY` from its process environment and holds it in memory only for the fixed-origin Authorization header. It never logs header values or arbitrary transport exception messages. Environment proxies and redirects are not used. Payloads, responses and recorded IDs are checked for credential contamination and refused rather than silently rewritten. HTTP error bodies are audited under the same check. All provider outputs remain untrusted text; the provider grants no shell or tool access.

The existing verifier forwards a fixed list of nonsecret environment variables, mounts sanitized source and sealed cache inputs read-only, drops capabilities, uses a read-only root filesystem, no new privileges, bounded RAM/CPU/PIDs, private tmpfs, and `--network none`. It mounts neither the repository root/`.git`, host home, GitHub token, API key, host secret files, nor Docker socket. No candidate build runs on the orchestration host. These verifier bytes are unchanged. The future cloud apparatus must repeat live isolation/cancellation probes before a coding launch; source inspection and synthetic tests do not prove cloud container behavior.

Trust boundary: the orchestrator host and operator are trusted. A privileged host administrator or compromised Docker daemon can inspect orchestration memory; this work does not claim to protect secrets from that administrator. Use a dedicated clean apparatus with no unrelated secrets. Exact third-party inputs must be audited for credentials before any transfer. Evidence should contain only recorded requests/responses, safe metadata and the existing scoped audit artifacts; never upload broad VM/home/environment/log directories.

The tiny API smoke does not start candidate code or a verifier. Its isolation evidence concerns requests and files only. Credential exclusion from actual remote candidate/verifier execution remains a live qualification obligation.
