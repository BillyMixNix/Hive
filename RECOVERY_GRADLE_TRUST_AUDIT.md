# Gradle verifier trust boundary

The recovered JVM verifier executes the candidate's Gradle build. In `hive_canonical/legacy/verification/jvm_runner.py:650–679`, targeted verification invokes Gradle `test --tests <frozen class>` and reads JUnit XML from `build/test-results/test`; the full path at `:702–735` similarly trusts Gradle task execution and reports. The host checks frozen test source identity and unchanged source after execution, but `hive_canonical/legacy/workshop/hive_jvm.py:225–295` does not bind arbitrary build-script bytes in its inspected profile.

This is an observed false-PASS boundary, not only a hypothetical risk. The reproducible model-free [probe](recovery/rc1-closure/gradle_trust_probe.py) and [result](recovery/rc1-closure/gradle-trust-probe.json) use the pinned image and Gradle 9.2.1. A genuine synthetic JUnit test fails (one case, one failure, Gradle exit 1). Changing **only** `build.gradle` redirects the test source set to a generated passing same-name class under `build/`; original test source SHA-256 stays `49b7459c47ba1aeea2e5b78796171f017a9aa2a3b8ad3f61c7e0cc73f943af52`. The attacked Gradle run exits 0 and emits one case/zero failures; recovered `_reports` and `_result_check` accept it as PASS. This synthetic probe does not rescore any historical J001 result. It shows why a candidate-controlled Gradle script cannot be trusted to authenticate frozen test execution. A separate disposable M3.2 profile probe found the pinned profile dictionary identical before and after a candidate `build.gradle` change, so profile equality alone is insufficient.

This audit chooses **fail-closed scope policy** rather than claiming general Gradle report-forgery resistance. For every detected Gradle profile, RC1 permits only application Java source paths beneath `src/main/java/` as worker write scope. Other writable paths, including scripts, wrapper, properties, version catalogs, convention plugins, tests and resources, raise the distinct host exception/classification `UNQUALIFIED_BUILD_CONTROL_SCOPE` before planner or worker execution. Independently of profile detection, Gradle authority basenames and directories are rejected at any nested path. The policy is general profile/path logic, not a J001–J004 filename list. It preserves the frozen J001–J004 application-Java scopes. The existing source inventory, scoped-edit preflight, and symlink/regular-file checks continue independently. This does not prove that every possible Gradle project treats application Java as independent of build-control logic; RC1's bounded replay remains limited to the frozen NeoForm profile.

Deterministic scope tests reject requests for `build.gradle`, `build.gradle.kts`, `settings.gradle`, `settings.gradle.kts`, `gradle.properties`, wrapper launchers/metadata, init scripts, version catalogs, buildSrc/build-logic, test source, resources, and non-Java paths. These pre-agent guards block build logic that could create custom tasks, modify dependencies/filtering/source sets, forge/delete reports, alter exit behavior, invoke subprocesses, or mutate verifier-visible files. Only source-set substitution was independently executed as a working exploit; the other listed surfaces are covered by conservative path rejection, not individual exploit demonstrations.

The policy does not establish that all Java source is intrinsically safe for every possible Gradle project. RC1 is qualified only for the source-only frozen M3.2 profile used by the bounded replay; unusual builds that treat application Java as build control require their own qualification. No verifier or frozen acceptance assertion is weakened.
